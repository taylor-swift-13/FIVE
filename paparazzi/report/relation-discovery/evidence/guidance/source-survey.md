## G1 — Horizontal command-mode substitution preserves the entire next reference (highest priority)

Entries: `gh_update_ref_from_pos_sp` H:105–141; `gh_update_ref_from_speed_sp` H:143–168; `gh_update_ref_from_accel_sp` H:170–188; common private limiter `gh_saturate_accel` H:203–214. Actual alternatives are dispatched in `guidance_h_update_reference` HC:273–299 (accel HC:290, speed HC:296, position HC:298). The entries do not call each other; this is a relational replacement/protocol property, supported by a real mode dispatcher.

Old state S=(p,v,a,dt,config). All three entries first compute q=fl(v*dt), r=fl(a*dt), integer p1=p+trunc(q*2^37), and v1=fl(v+r), componentwise and in that exact source order. For speed input u define e=fl(v1-u), c=fl(e*(-inv_tau)), using the two assignments at H:159,162. Compare speed(S,u) with accel(S,c): expected identical next p, speed, accel and unchanged configuration, fieldwise float-bit equality. For position input t, compute p1/v1 as above; epos=POS_FLOAT_OF_BFP(t-(p1>>(37-INT32_POS_FRAC))); vel=fl(epos*(omega*0.5/zeta)) with the actual literal types; apply the exact speed limiter H:190–201 to vel; then c=fl(fl(vel-v1)*(2*zeta_omega)). Compare position(S,t) with accel(S,c): same target observation. This explicit raw-command relation allows saturation to be active and is not an assumption of equal outputs.

Value: switching reference modes need not introduce a one-cycle trajectory discontinuity when the new feedforward acceleration matches the old controller demand. Integration deliberately uses the previous acceleration, so computing c from OLD speed is generally wrong. Saturation only changes the newly stored acceleration, not the current tick speed.

Domain: finite bounded v,a,dt and commands; each float-to-int64 conversion representable; p additions and position-error integer arithmetic representable; finite nonoverflowing norm squares; nonnegative finite max_speed and max_accel; nonzero zeta for positional branch. Restrict to finite values to avoid NaN payload/external-lib variation. Pin IEEE operation/literal evaluation and sqrtf; binary32 state alone does not determine all expression types (`0.5` is double). Equality is exact between the two executions using the SAME generated c bits; this does not assert zero error relative to a real-valued controller. No speed envelope is guaranteed by these APIs.

## G3 — A change of horizontal position origin commutes with all three reference modes (high priority)

Entries H:105,143,170 and optional reset `gh_set_ref` H:95. No calls between the entries; this is a cross-entry family of frame-invariance relations, extending G1 without demanding controller gains coincide.

Choose integer position-grid displacement d=(dx,dy), K=2^(37-INT32_POS_FRAC). Related old states have pB=pA+K*d and identical v,a,dt,configuration. In position mode relate inputs tB=tA+d; in speed/accel mode use identical input bits. Target: after either matched entry, pB'=pA'+K*d, while speed, acceleration and configuration are fieldwise bit-identical. The shared integer integration H:112–117/150–155/177–182 preserves offset exactly; the position error H:121–122 cancels a grid-aligned displacement before converting to float. Translation does not enter float arithmetic. Optional initialization protocol uses correspondingly translated `gh_set_ref` inputs then the same command relation.

Value: guidance behavior should not depend on NED local-origin choice; exact invariance is available despite float feedback because subtraction precedes float conversion. Quantify over a nonzero range of translations, not just d=0.

Domain: both executions stay within int64 p bounds, int32 setpoint bounds, intermediate position-error/subtraction ranges and float-to-int conversion bounds; target arithmetic signed right shift is pinned. All K*d/translated values are representable. Negative signed left shifts in reset H:98–99 are a separate C definedness issue; formulate the update relation directly on well-formed states, or restrict reset inputs/translation domain appropriately until target semantics are explicitly fixed. Arbitrary sub-grid translations do not cancel through the right shift and are not covered. This is exact integer-offset plus float-bit equivalence, not an approximate rotational/translation theorem over arbitrary real offsets.

## G4 — Altitude and climb modes share a bounded, inward-pointing vertical reference envelope (medium priority, fixedpoint)

For either entry, old (z,v,a), same integration vpre=v+a and zpre=z+v precedes command computation. Under defined integer arithmetic, let L/H be GV_MIN_ZD/GV_MAX_ZD and Amin/Amax be GV_MIN_ZDD/GV_MAX_ZDD. Expected next-state common relation: v'=clamp(vpre,L,H), Amin<=a'<=Amax, v'=L implies a'>=0, and v'=H implies a'<=0. Assume L<H and Amin<=0<=Amax. Position mode z'=zpre; climb mode z'=clamp(zpre,cur_z-D,cur_z+D), D=GV_MAX_Z_DIFF. Hence a per-mode position relation accompanies the common speed/accel envelope. Following actual publication VC:295–298 scales the same invariant into controller units if conversion/left-shift definedness is separately met.

Value: changing between altitude and climb modes preserves the speed-limit compatibility contract; at a boundary the next acceleration cannot push farther outward. Climb mode also caps altitude lookahead relative to measured z_pos. It does not establish physical flight-state limits or indefinite closed-loop stability.

Domain: pin airframe constants and fixedpoint shifts; prove safety of z+v, v+a, products in raw controllers and all narrowing conversions, including both branch-specific error computations, before relying on post-computation saturation. No floats at runtime in the reference update arithmetic (floating literals only configure fixedpoint constants). This is a common exact integer predicate across different next states, not equality of altitude/climb trajectories. Input raw demands generally differ. Raw command equality plus an inactive climb-position clamp would be needed for exact mode equivalence.

## Rejected overclaims and selection guidance

Do not state general exact position-mode=speed-mode with speed setpoint equal to positional vel_sp: position uses fl((vel-v1)*(2*zeta_omega)), speed uses fl((v1-vel)*(-inv_tau)), with distinct gain defaults, subtraction order and rounding/signed-zero behavior. A numerical refinement would need gain calibration, a domain away from saturation branch thresholds, a roundoff analysis and a stated error bound. Also do not assert exact Euclidean accel <= max_accel after H radial saturation without a floating error allowance: rounded norm/sqrt/multiplication can overshoot; overflow can produce Inf*0/NaN. H speed mode does not call gh_saturate_speed. V climb and altitude differ in position clamping. These limitations make G1/G2/G3 the preferred floating-centered paper candidates; G4 is a useful fixedpoint fallback.
